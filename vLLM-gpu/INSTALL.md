Deploy a production-ready enterprise large-model inference gateway in an NVIDIA GPU (CUDA) environment. This directory covers only the real GPU production path.

Staged K8s deployment package: `deploy/` (Stage 1 single engine -> Stage 2 LMCache shared KV -> Stage 3 Prefill/Decode + DCGM monitoring).  
CPU-based lab counterpart: `../vLLM-cpu/deploy` (CPU simulation following the same staged narrative).

Hardware prerequisites (adapt to the actual machines): at least one NVIDIA GPU (at least 24 GB of VRAM is recommended for running `Qwen2.5-7B` at half precision; use quantization or a smaller model with less VRAM), a compatible CUDA driver, and nvidia-container-toolkit. GPUs must be schedulable from K8s through the Device Plugin or GPU Operator. Production cross-node PD also requires an RDMA network such as InfiniBand, RoCE, or EFA.

1. Core Features to Implement

- Production model foundation: use `Qwen/Qwen2.5-7B-Instruct` by default (half precision consumes roughly a dozen or more GB of VRAM, with additional usage depending on KV and concurrency). The goal is real conversational quality and throughput; temporarily switch to `--load-format dummy` only for troubleshooting or profiling.
- VRAM page pool (PagedAttention): allocate the KV page pool in GPU VRAM. The official default is `gpu_memory_utilization=0.92` (see the vLLM CacheConfig/LLM documentation); tune it further for fragmentation and multiple instances on the same GPU.
- Behavior when KV capacity is insufficient (V1): official V1 **removed** GPU-to-CPU KV Cache Swapping. The default preemption mode is **RECOMPUTE** (the entire request releases its KV blocks and recomputes them later; the engine does not silently overwrite a session that is still running). Follow the official optimization guidance to mitigate this: increase `gpu_memory_utilization`, decrease `max_num_seqs` or `max_num_batched_tokens`, or increase TP/PP.
- Practical default versus advanced deployment (keep the distinction clear): **most production deployments with multiple replicas let each GPU replica manage its own local KV without sharing it** (as stated publicly by IBM Research and others). Each instance retains KV for requests in progress and can use Automatic Prefix Caching for in-process reuse. A more common compromise than shared storage is **session stickiness, prefix hashing, or KV-aware routing**, which sends traffic to a replica that already has the cache. A **Mooncake or LMCache cluster-wide shared pool** is an advanced option for large-scale, multi-turn, agent, PD, and similar workloads. It requires explicit integration and is not built into a bare multi-replica `vllm serve` deployment. See section 0.1 of `OPTIMIZATION.md`.
- Single-process prompt prefix caching (Automatic Prefix Caching): this is usually enabled by default on V1 (`enable_prefix_caching` defaults to True). Identical prefixes can skip prefilling the shared segment; the official documentation states that it primarily reduces prefilling and does not reduce decoding. Its scope is **one engine**, not multiple replicas.
- Cross-replica KV sharing (advanced, not the default): multiple GPU replicas plus Mooncake Store or LMCache, with a hot DRAM/RDMA tier and an optional cold tier backed by shared object storage such as S3. A connector must be configured explicitly. This is a different layer from in-process APC and from RECOMPUTE inside the V1 engine.
- Chunked Prefill: official V1 enables it by default "whenever possible." Scheduling prioritizes decode, then uses the `max_num_batched_tokens` budget to process or split prefill work. Follow `OPTIMIZATION.md` when tuning: a smaller budget favors ITL, a larger budget favors TTFT, and `>8192` is often recommended for throughput with a small model on a large GPU.
- PD disaggregation (Prefill/Decode): this separates Prefill from Decode; it is not Data Parallelism. The Prefill pool handles compute-intensive long prompts, while the Decode pool handles token generation and KV bandwidth. A proxy/router, or Dynamo or `vllm-router` in PD mode, provides a unified external OpenAI endpoint. Transfer KV with `NixlConnector` or `MooncakeConnector` (direct GPU transfer; production Dynamo deployments use RDMA/NIXL). These can be combined with LMCache in a `MultiConnector`: the current request uses P-to-D handoff, while cross-request reuse uses the shared cache. Set `kv_role=kv_producer` on the Prefill side and `kv_role=kv_consumer` on the Decode side. At least one GPU, or one GPU pool, is recommended for each role. Acceptance criteria should verify that long prompts and in-flight decode requests do not block each other, and should measure TTFT/TPOT, handoff failure rate, and independent scaling of Prefill and Decode.
- PD Pod scheduling and high-speed interconnects (following the NVIDIA Dynamo documentation):
  1. Transport layer: production PD must use RDMA (InfiniBand, RoCE, or AWS EFA) plus NIXL (UCX/libfabric). The Dynamo "Disaggregated Inference Communication Guide" states that cross-Pod KV handoff between K8s Pods **cannot** rely on NVLink. Without RDMA, using TCP can degrade TTFT by approximately 200-500 times. Even if P and D occasionally run on the same host, a consistent RDMA transport is recommended.
  2. Resources and permissions: request one RDMA device allocation per GPU (the documentation example uses an `rdma/ib` count equal to the GPU count); add `IPC_LOCK` and `SYS_RESOURCE` to the container.
  3. Placement: nodes must have at least a `topology.kubernetes.io/zone` label, or an equivalent rack label. **Balance Prefill and Decode capacity** within each topology domain (for example, the Dynamo example uses a 1:2 P:D ratio within a domain).
  4. Routing: Topology-Aware KV Transfer lets the router select Decode workers in the same topology domain as Prefill by using `required` or `preferred`. Scheduling alone, without same-domain routing, can still transfer KV across domains.
  5. Source documentation: https://docs.nvidia.com/dynamo/v1.4.1/knowledge-base/kubernetes/kubernetes-operator/disagg-communication and https://docs.nvidia.com/dynamo/v1.4.2/knowledge-base/kubernetes/multinode/topology-aware-kv-transfer
- Production-grade external service and observability: expose an OpenAI-compatible HTTP interface. `/metrics` must export Prometheus metrics, including real `gpu_cache_usage_*`, throughput, latency, and preemption metrics.

2. Recommended Implementation and Technology Choices

- Compute foundation: NVIDIA CUDA. Use the official CUDA-enabled PyTorch build and a matching vLLM GPU wheel, or build vLLM from source against CUDA.
- Environment isolation: create an independent Python 3.11 environment with Conda or venv, such as `vllm-gpu`; install the CUDA-enabled `torch`, then install `vllm`.
- Model loading: default to `--model Qwen/Qwen2.5-7B-Instruct` and `--dtype auto`, or use `bfloat16` or `float16`. If VRAM is limited, use AWQ, GPTQ, FP8, or another quantization method, or switch to a smaller Instruct model.
- System-level tuning: use [Optimization and Tuning](https://docs.vllm.ai/en/stable/configuration/optimization/) as the authority. After confirming the default APC and chunked prefill state on a single replica, tune `gpu_memory_utilization` (the documented default is 0.92), `max_num_seqs`, `max_num_batched_tokens`, and `max_model_len`; monitor preemption with Prometheus. For multiple replicas, start with KV-aware routing; add Mooncake/LMCache only when cross-replica reuse is needed. For PD, use `NixlConnector` or `MooncakeConnector` with Dynamo topology placement and RDMA.
- Multiple GPUs: use `--tensor-parallel-size` for multiple GPUs on one host, then `pipeline_parallel_size` across hosts. Scale Prefill and Decode pools independently; do not confuse this with TP.

Automation Steps for Cursor

1. Step 1: check the NVIDIA driver, `nvidia-smi`, and CUDA visibility; create and activate the `vllm-gpu` environment.
2. Step 2: install the CUDA-enabled torch and vLLM from the official GPU index or wheel.
3. Step 3: write the GPU launch command with the model, dtype, VRAM threshold, `max_num_seqs`, `max_num_batched_tokens`, and port `8000`; add KV-aware routing, Mooncake/LMCache, or PD (Prefill/Decode + NIXL/RDMA) configuration when needed.
4. Step 4: validate streaming chat/completions; inspect `gpu_cache_usage_*`, latency, throughput, and preemption in `/metrics`; for PD, also test isolation between a long prefill request and concurrent short decode requests.
