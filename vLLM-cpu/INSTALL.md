The requirement is to perfectly simulate an enterprise-grade large-model inference gateway through virtualization and mock flags in a GPU-free, CPU-only environment with an AMD 5800H and 64GB of memory.

## 0. Align With Production Defaults First

Avoid treating this exercise as the default production architecture for everyone.

- **Most production deployments with multiple replicas:** Each Pod manages its own local KV cache and **does not share it across Pods by default**. Each instance retains the KV cache for requests currently running on it and can use in-process Automatic Prefix Caching.
- **A more common compromise than shared storage:** Session affinity, prefix hashing, or KV-aware routing sends requests to replicas that are likely to have the relevant local cache, while storage remains unshared.
- **Mooncake or LMCache cluster sharing:** These are explicitly introduced only for advanced large-scale, multi-turn, Agent, or PD scenarios. The network-distributed prefix cache and SeaweedFS described later in this directory **deliberately simulate this advanced layer**; they are not built into a basic multi-replica vLLM deployment.
- **V1 GPU comparison:** The engine no longer relies on SWAP eviction. When capacity is exhausted, its default behavior is preemption with RECOMPUTE; retaining KV across storage tiers uses an external cache. See `../vLLM-gpu/OPTIMIZATION.md`, sections 0 and 0.1.

## 1. Core Features to Implement

- **Toy model foundation:** Use `facebook/opt-125m`, approximately 250MB, by default. It is commonly used for industry integration testing and is the baseline model for vLLM examples and LMCache CPU end-to-end tests. This exercise validates operational capabilities rather than generation quality. For faster startup, use `--load-format dummy`, which reads only the architecture configuration and fills the weights randomly. Memory is still allocated at the 125M scale instead of consuming tens of gigabytes as a 7B model would.
- **Virtual GPU memory page-table pool with PagedAttention:** Explicitly reserve an independent "virtual GPU memory page-table" pool in system memory and limit its usable saturation threshold.
- **Forced eviction of inactive KV cache with Swap:** Reserve a 16GB region from the 64GB of physical memory as the CPU host-memory swap area. When test traffic fills the virtual GPU memory pages, the system must automatically trigger the control flow that swaps inactive KV data out to this memory swap area.
- **Single-process prompt prefix caching:** `--enable-prefix-caching` reuses KV pages by prefix hash only within the same vLLM process. On the second request with an identical prefix, the hit count increases and TTFT decreases. Dummy weights do not affect this metric. Time to first token becomes shorter, but not zero.
- **Network-distributed prefix cache:** This is only an operations exercise covering cross-Pod hits, eviction, and `/metrics`; generated-text correctness does not matter. Run at least two vLLM Pods in k3s context `108`, all using `facebook/opt-125m`, and run an in-cluster `lmcache server` exposed through ClusterIP. Every Pod connects to the same service through `LMCacheMPConnector` instead of relying on shared local `/dev/shm`. Hot KV data is sent to LMCache over the network, while the cold tier can reside in SeaweedFS in the same cluster. After Pod A writes a prefix, a request to Pod B should register one hit. Once LMCache is connected, disable in-process `--enable-prefix-caching` and let the external cache handle reuse. Keep the prefix-hash algorithm identical across instances. Two 125M Pods plus LMCache and SeaweedFS easily fit in 64GB. For a multi-Pod exercise, still reduce `--max-model-len`, `--swap-space`, and `--gpu-memory-utilization` to leave memory for the cache tier. The 5800H has only 8 cores, so multiple Pods compete for CPU and requests are slower, but this does not prevent observing cross-Pod hits and eviction. Text is readable with real weights. With dummy weights, decoded output is meaningless, but hit metrics remain valid.
- **Network-shared disk KV cache:** Store the cold tier in a distributed file service in k8s instead of a local directory, allowing multiple vLLM Pods to share the same KV data. Local k3s context `108` uses the existing `kubeflow/seaweedfs` ClusterIP service, with Filer on `8888` and S3 on `8333`, as the LMCache remote backend. Hot KV data can remain in memory or `/dev/shm`; overflow is written to SeaweedFS over the network. Multiple Pods connect to the same LMCache remote backend instead of mounting separate `local-path` volumes. Operational observations focus on cross-Pod hits, network latency, bandwidth, and storage quotas rather than local directory size. This differs from vLLM `--swap-space`: `--swap-space` reserves an eviction area only in process memory and does not write files. The prefix-hash algorithm must be consistent across instances. SeaweedFS stores only KV chunks; the model itself remains the local `opt-125m`, approximately 250MB, or a dummy architecture configuration.
- **Rate control with Chunked Prefill:** Time-share compute capacity. Force long-text requests to be processed in chunks to simulate protecting ordinary Decode users from latency jitter under high-throughput, high-concurrency load.
- **PD disaggregation topology exercise for Prefill and Decode:** Practice deployment and operations only, without expecting acceleration. In k3s, run at least one Prefill Pod and one Decode Pod, both using `facebook/opt-125m`, behind a proxy or router. A request first reaches Prefill to compute KV, then passes to Decode for token generation. Prefer `NixlConnector` on the CPU path for KV handoff with `kv_buffer_device: "cpu"`. If installing NIXL is difficult, use lightweight fake PD: Prefill writes to shared LMCache or SeaweedFS, and Decode retrieves by key. On the 8-core 5800H, Prefill and Decode compete for the same cores and disaggregation is often slower. Acceptance criteria should cover routing, handoff, failure retries, and `/metrics`, not higher tokens/s. This is not Data Parallel.
- **Production-grade external service and observability:** Expose an OpenAI-compatible HTTP API and real production-grade Prometheus monitoring metrics in real time through `/metrics`.

## 2. Recommended Implementation and Technology Choices

- **Compute-platform substitute:** Set `export VLLM_PLATFORM=CPU` to force the inference engine to stop searching for NVIDIA CUDA or AMD ROCm GPUs and switch directly to the CPU executor backend, using CPU multithreading to simulate GPU computation.
- **Environment isolation:** Use Conda to create an isolated Python 3.11 environment named `vllm-mock`, and install the CPU build of the foundational numerical framework PyTorch from the official CPU package index.
- **Model loading:** By default, `--model facebook/opt-125m` loads approximately 250MB of real weights. To skip downloading weights, add `--load-format dummy`, or the equivalent `VLLM_TEST_FLAGS="dummy_weights=1"`, to read the architecture and fill weights randomly.
- **Persist system-level tuning parameters:** For the single-process exercise, specify `--model facebook/opt-125m`, `--gpu-memory-utilization 0.60`, `--enable-prefix-caching`, `--enable-chunked-prefill true`, and a moderate `--swap-space` in the startup command. It only needs to demonstrate eviction; reserving 16GB as if the model were 7B is unnecessary. For the network-distributed prefix-cache exercise, connect each vLLM Pod to the in-cluster `lmcache` Service, use reduced values for `--max-model-len`, `--swap-space`, and `--gpu-memory-utilization`, and disable `--enable-prefix-caching`. For the network-disk exercise, keep SeaweedFS available and point the LMCache cold tier to `seaweedfs.kubeflow.svc`, preferably S3 on `8333` or alternatively Filer on `8888`. All vLLM Pods share one remote path, such as the `kv-cache` bucket or directory, while retaining a small CPU buffer for remote reads and writes. For the PD exercise, set `kv_role=kv_producer` on Prefill and `kv_role=kv_consumer` on Decode, or share only LMCache keys for fake PD. The proxy continues to expose one unified OpenAI endpoint.
